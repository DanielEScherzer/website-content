# RSPHP Part 2: Build Tools

In my [last post][blog-rsphp-sys], I talked about the `rsphp-sys` crate, which
provides Rust bindings for PHP's C ABI to help build PHP extensions in Rust. As
I mentioned, I fully expect extension developers to override the definition of
the `rsphp-sys` crate to customize their bindings. In order to facilitate those
overrides, most of the build logic comes from a separate crate,
[`rsphp-build-tools`][crate-build-tools].

The latest version of the build tools crate, version 0.1.3
([documentation][docs-build-tools-013]), provides seven different utilities for
use in the `rsphp-sys` build script. Five are structs that implement bindgen's
[ParseCallbacks][bindgen-parsecallbacks-t] trait, one is a tool for iterating
over PHP's C header files, and the last is a utility for running the
`php-config` command.

References to PHP use the latest stable release as of writing (PHP 8.5.13),
likewise with Rust (Rust 1.100.0).

## ParseCallbacks

There are two primary methods to override bindgen's default behavior or add
configuration. The first is calling the various methods on the
[Builder instance][bindgen-builder] to set options directly, like which files
should be parsed and what types/functions/variables/etc. should have bindings
generated. The second is by using the
[`parse_callbacks()` method][bindgen-parsecallbacks-m] to add sets of callbacks
(objects implementing the `ParseCallbacks` trait) to the builder. By putting as
much logic as possible in those callbacks, the build script just needs to add
the callbacks to the builder.

The five `ParseCallbacks`-implementing types that the build tools crate provides
are:

### AnonymousTypeNames

The [`AnonymousTypeNames`][docs-AnonymousTypeNames] struct renames some types
from the ones generated by bindgen to slightly clearer names. PHP's C ABI
includes a number of anonymous structs and unions which need to be named to
represent them in Rust.

Bindgen generates names like `_zend_function__bindgen_ty_1` or
`_zval_struct__bindgen_ty_1__bindgen_ty_1__bindgen_ty_1`, with
`__bindgen_ty_{counter}` being appended to the name of the containing type. The
`AnonymousTypeNames` struct adjusts some of the auto-generated names to be a bit
clearer, e.g. `_zend_function__common` and `_zval_u1_v_u` for those two.

### BuildIdCallbacks

The [`BuildIdCallbacks`][docs-BuildIdCallbacks] struct is used to replace the
definition of the `ZEND_MODULE_BUILD_ID` C macro with one that bindgen can
understand. That macro, split here over multiple lines for readability, is
[defined as][gh-ZEND_MODULE_BUILD_ID]:

```c
#define ZEND_MODULE_BUILD_ID "API" ZEND_TOSTR(ZEND_MODULE_API_NO) ZEND_BUILD_TS \
	ZEND_BUILD_DEBUG ZEND_BUILD_SYSTEM ZEND_BUILD_EXTRA
```

and draws on definitions from [zend_build.h][gh-zend_build]

```c
#define ZEND_TOSTR_(x) #x
#define ZEND_TOSTR(x) ZEND_TOSTR_(x)

#ifdef ZTS
#define ZEND_BUILD_TS ",TS"
#else
#define ZEND_BUILD_TS ",NTS"
#endif

#if ZEND_DEBUG
#define ZEND_BUILD_DEBUG ",debug"
#else
#define ZEND_BUILD_DEBUG
#endif

#if defined(ZEND_WIN32) && defined(PHP_COMPILER_ID)
#define ZEND_BUILD_SYSTEM "," PHP_COMPILER_ID
#else
#define ZEND_BUILD_SYSTEM
#endif

/* for private applications */
#define ZEND_BUILD_EXTRA
```

<!-- Stringizing: n3220 6.10.5.2 -->
The `ZEND_TOSTR` macro makes use of C's "stringizing" operator to convert the
value of the argument (here the value of the `ZEND_MODULE_API_NO` macro) into
a character literal. After substituting the parts of the build ID, the
definition might look something like the following (for a debug, NTS build on
PHP 8.6)

```c
#define ZEND_MODULE_BUILD_ID "API" "20261112" ",NTS" ",debug"
```

<!-- Concatenation: n3220 5.1.1.2 step 6 -->
At that point, the macro definition takes advantage of the fact that C
concatenates adjacent string literals into a single string to result in the
overall build ID, in this case `"API20261112,NTS,debug"`.

The combination of the `ZEND_TOSTR` macro and the concatenation of the different
parts of the build ID mean that the `ZEND_MODULE_BUILD_ID` definition cannot be
generated by bindgen's default handling.

For other constants, I would probably just say "oh well" and move on, but the
build ID is part of the module definition of PHP extensions. It must be present
in the module entry, and must match the ID of the PHP engine, for extensions to
be loadable. As a result, I wrote the `BuildIdCallbacks` type, implementing
macro-processing callbacks to read in the definitions of `ZEND_MODULE_API_NO`,
`ZEND_BUILD_TS`, and `ZEND_BUILD_DEBUG` and then updating the definition of
`ZEND_MODULE_BUILD_ID`.

### CommentProcessor

The [`CommentProcessor`][docs-CommentProcessor] struct is probably not as useful
to extension developers, but I figured it was still worth factoring out. All it
does is add backticks in the documentation comment of the
`zend_ini_parse_quantity` function declaration
([source][gh-zend_ini_parse_quantity]) so that the indented parts of that
comment are treated by rustdoc as plain text. Otherwise

1. Per the [CommonMark spec for markdown][commonmark-spec] the indented lines are
treated as a code block (section 4.4).
2. The code block, since it is missing a declared language, is assumed by rustdoc
to be Rust ([documentation][rustdoc-assume-rust]).
3. The documentation, since it is not valid Rust code, triggers the
[`invalid_rust_codeblocks` lint][rustdoc-lint].

Since I use these build tools for the version of `rsphp-sys` that is documented
on docs.rs, I want the `zend_ini_parse_quantity()` documentation to treat the
indented parts of the comment as text -
[see the result][docs-zend_ini_parse_quantity]. But, others probably aren't
going to be generating the documentation for their overridden `rsphp-sys`
dependency, in which case they are free to skip using the `CommentProcessor`.
